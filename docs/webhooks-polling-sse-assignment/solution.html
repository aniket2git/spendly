Part 1 • FoundationsThe one problem behind all 10 questions

Every question in this paper is a different answer to the same single problem. Understand the problem properly and the ten questions stop being ten separate facts to memorise.

1.1 The rule that causes all the trouble

Story box • the strict teacher Imagine a classroom with a very strict rule: the teacher is not allowed to speak unless a student asks a question first. She can answer beautifully, in detail, as often as you like. But she can never call out "Ravi, your exam result just arrived!" She must wait to be asked.

That is exactly how plain HTTP works. The browser (client) must send a request first. Only then may the server reply. The server can never start the conversation.
Definition box
  • Pull (also called client-initiated): the client asks, the server answers. A normal API call is a pull.
  • Push (also called server-initiated): the data arrives without the receiver having just asked for it.
Plain HTTP only gives you pull. Every technique in this paper is a trick to get something that feels like push.

1.2 The five ways around the rule

Here is the whole paper on one page. Do not try to memorise it yet – just notice that the five techniques differ in only three things: who starts, how long the connection stays open, and which direction data flows.

The distinction that earns the most marks in this paper Webhooks are for server-to-server. The other four are mainly for browser-to-server. A webhook needs the receiver to have a public URL that can accept an HTTP POST, which a browser tab does not have. That is why a webhook receiver is typically a small server application – for example a trivial Flask app.

Part 2 • Question 5Short polling

Story box • "are we there yet?" You are on a long car journey. Every two minutes you ask your father: "are we there yet?" and every time he answers immediately – usually "no, not yet". Occasionally, finally, "yes, we have arrived".

You got your answer eventually, but look at the cost: dozens of questions, and almost every single answer was useless. That is short polling, also just called polling.
Definition box • short polling The client sends a request at fixed, repeating intervals. The server replies immediately every time – even when it has no new data, in which case it sends back an empty result. The connection is closed after each reply and opened fresh for the next one.

Part 3 • Questions 6 and 3Long polling

Story box • "hold the line" You ring the exam office and ask "are my results out?". Instead of saying "not yet, call back in five minutes", the clerk says: "stay on the line, do not hang up. The moment they arrive I will tell you."

You make one phone call instead of twenty. And the instant the news exists, you hear it – no waiting for your next scheduled call. That is long polling.
Definition box • long polling The client sends a request. If the server has no data, it does not reply – it holds the connection open and stays silent. As soon as data becomes available it sends the response and closes. The client then immediately opens a new request, and the cycle repeats.

3.2 The "persistent connection" trap

Question 3 contains a subtle option about persistent connections. You must be precise here.

Definition box A persistent connection means one connection that is deliberately kept alive across many messages, as its normal way of working – like a WebSocket or an SSE stream.

Short polling has the opposite design: every poll is a brand-new, independent, short-lived request that is closed as soon as it is answered. So polling does not require a persistent connection. It works perfectly well without one – that is precisely why it is the crudest technique and also the easiest to deploy anywhere.
Trap box • do not confuse these two Long polling holds one request open while it waits for an answer. That is not the same as a persistent connection carrying many messages. And the statement in Q3 is about polling in general, which certainly does not require it.

Part 4 • Question 4Server-Sent Events (SSE)

Story box • the railway station loudspeaker You reach the railway platform and switch on your ears. You do not ask the announcer anything. He simply keeps announcing, whenever there is something to announce: "train 5 minutes late" ... "platform changed to 3" ... "train arriving now".

You listen. You cannot talk back through the loudspeaker – it only works in one direction. That is Server-Sent Events: you open the channel once, then the server keeps pushing announcements down it for as long as you stay connected.
Definition box • SSE The client opens one long-lived HTTP connection. The server keeps it open and streams a sequence of events down it, in a special text format (content type text/event-stream). Communication is one way only: server to client. In the browser you consume it with the built-in EventSource object.

4.1 What SSE actually looks like in code

# SERVER: an ordinary Flask route that never stops yielding
from flask import Flask, Response
import time

app = Flask(__name__)

def event_stream():
    while True:
        price = get_latest_price()
        yield f"data: {price}\n\n"      # the SSE text format
        time.sleep(1)

@app.route('/stream')
def stream():
    return Response(event_stream(), mimetype='text/event-stream')

// CLIENT: three lines, using the browser's built-in EventSource
const source = new EventSource('/stream')

source.onmessage = (event) => {
  console.log('server says:', event.data)   // fires again and again
}
Notice what is NOT in that code There is no message broker. No Celery. No Redis. No task queue. No navigator.serviceWorker.register(...). SSE is just a Flask route that keeps yielding, and a browser object that keeps listening. Keep that in mind for the question below.

Option-by-option reasoning

OptionTrue or falseWhy
ATRUE That is the definition of SSE, word for word: a server-side mechanism for pushing events to the client. Figure 4.1.
BFALSE
the answer		 A task queue plays no part in SSE. Look again at the code in section 4.1: a Flask route that yields, and a browser object that listens. When two options look shaky, always pick the one that is false beyond any doubt.

Part 5 • FoundationsWebSockets

Story box • the walkie-talkie that never switches off SSE was a loudspeaker: the announcer talks, you only listen. A WebSocket is a proper phone call. Once the call connects, either person can speak at any moment, as often as they like, without hanging up and dialling again.

This is why chat apps, multiplayer games and live collaborative editors use WebSockets: both sides genuinely need to send.
Definition box • WebSocket A WebSocket starts as an ordinary HTTP request that asks to "upgrade" the connection. Once the server agrees, the connection switches to the WebSocket protocol (ws:// or the secure wss://) and stays open. From then on it is full duplex: both client and server can send messages independently, at any time.

5.1 SSE vs WebSocket – the one difference that matters

Say it out loud once "SSE is a loudspeaker: one way. A WebSocket is a phone call: two ways."

Part 6 • Questions 1, 2, 7 and 10Webhooks

Four of the ten questions are about webhooks, so this is the part worth reading twice.

Story box • "do not call us, we will call you" You order a cake from a bakery. Two ways to find out when it is ready:

The polling way: you phone the bakery every ten minutes. "Ready?" "No." "Ready?" "No." Annoying for both of you.

The webhook way: you leave your phone number with them and go home. When the cake is ready, they ring you. One call, perfectly timed, zero waste.

A webhook is that phone number. You register a URL with someone else's system, and when an event happens, their server sends an HTTP POST to your URL. It is often described as a reverse API: instead of you calling them, they call you.
Definition box • webhook A webhook is a user-defined HTTP callback. You give a provider a public URL. When a chosen event occurs, the provider sends an HTTP POST request to that URL, carrying the event details in the request body. It is event-driven, server-initiated, and one way: they send, you acknowledge, the connection closes.

6.1 Why the receiver must answer immediately

Story box • the courier at your door A courier rings your bell. All he needs is your signature – five seconds. He does not want to stand there while you unpack the parcel, read the manual and assemble the furniture. If you make him wait, he marks the delivery as failed and comes back tomorrow.

A webhook sender is that courier. It wants a quick 200 OK signature. If your receiver is slow, the sender times out and assumes delivery failed – and most providers then retry, so you can end up processing the same event several times.

6.2 Can a webhook be secured? Yes.

One option in Question 1 claims a webhook cannot be secured if its URL is public. That is wrong, and here is the standard toolkit that proves it.

The idea to carry away A URL being reachable by anyone does not mean it is trusted by anyone. Your front door is publicly reachable too – that is why it has a lock. The webhook's lock is the signature.

  • A. A Webhook pushes the messages to an application.
  • B. In general, webhook pulls the messages from an application, but an API pushes the messages to an application.
  • C. Webhooks are generally synchronous in nature.
  • D. An API can pull and push the messages from/to an application.
This is the one answer to change Your screenshot has A, C and D ticked. Options A and D are right, but option C should not be ticked. The correct answer is A and D. The reasoning is below, and it is worth reading carefully because this exact distinction comes up again and again.

Option-by-option reasoning

OptionVerdictWhy
ATRUE A webhook pushes: the provider sends an HTTP POST into your application without being asked. Right-hand side of Figure 6.4.
BFALSE The two words are swapped round. Webhooks push, APIs pull. This option says the exact opposite of the truth, which is the most common trick in the whole topic.
CFALSE
change this		 Webhooks are asynchronous in nature, not synchronous. They are the standard example of event-driven communication: the receiver never asks and never waits, it simply reacts whenever an event happens to arrive. Synchronous is the word for the API model, where the caller sends a request and blocks until the answer comes back. See the detailed explanation below.
DTRUE An API is two-directional in this sense: GET pulls data out of an application and POST or PUT pushes data into it. A webhook, by contrast, only ever pushes.

It is worth being precise, because there is a grain of truth that traps people.

A consistency check you can do inside the exam hall Question 8 of this very paper asks about pub/sub and marks "the communication is asynchronous in nature" as correct while "synchronous" is wrong. A webhook is the same shape of thing: an event happens, a message is pushed, the receiver reacts later. It would be inconsistent for the paper to call one asynchronous and the other synchronous. Part 7 • Questions 8 and 9Pub/Sub and the message broker

7.1 What is publish-subscribe?

Story box • the school notice board The head teacher has news: "sports day is on Friday". She does not walk to each of 600 students and tell them one by one. She does not even know who is interested. She pins one notice on the board under the heading "SPORTS".

Everyone who cares about sports has already decided to watch that heading. All of them read the same notice. The head teacher never learns their names.
  • The head teacher = the publisher.
  • The heading "SPORTS" = the topic.
  • The students watching that heading = the subscribers.
  • The notice board itself = the message broker.
Definition box • pub/sub A publisher sends a message to a named topic, not to a particular receiver. The broker then delivers a copy to every subscriber of that topic. The publisher does not know who the subscribers are, how many there are, or whether there are any at all. This is called fan-out, and the not-knowing is called decoupling.

The point that Question 8 tests In pub/sub the broker's job is to hand the message to the topic's subscribers straight away – that is the whole idea of a topic. This "deliver it now to everyone listening" behaviour is what makes pub/sub suitable for live event notification, and it is entirely compatible with the communication being asynchronous: asynchronous means the publisher does not stop and wait, not that delivery is slow.
Question 8 1 mark • select all that apply

Which of the following is correct regarding pub/sub messaging?

  • A. It can be used to enable event driven architecture.
  • B. Any message published to a topic should be immediately received by the subscriber(s) of the topic.
  • C. The communication is synchronous in nature.
  • D. The communication is asynchronous in nature.

Option-by-option reasoning

OptionVerdictWhy
ATRUE Pub/Sub is the standard building block of event-driven architecture: publish an event, and any number of services react independently. Bottom band of Figure 7.1.
BTRUE A topic is not a storage locker. When a message is published, the broker delivers it to the subscribers of that topic right away. In classic pub/sub the message is broadcast to whoever is currently subscribed and then discarded – there is no waiting around for someone to come and collect it later.
CFALSE Direct opposite of D, so exactly one of the pair can be right. Synchronous would mean the publisher blocks until every subscriber has finished processing – which would destroy the whole point of decoupling.
DTRUE The publisher fires the message and carries on immediately. It does not wait for subscribers, does not know if they succeeded, and does not care. That is asynchronous.
Answer to Question 8 A, B and D
Matches the options you had selected.
Do B and D contradict each other? No – and this is worth understanding They describe two different sides of the exchange, so both can be true at once:
  • B is about the receiving side: once published, subscribers are handed the message immediately rather than having to poll for it.
  • D is about the sending side: the publisher does not block waiting for anyone.
"Immediate delivery" and "the sender does not wait" are perfectly compatible. Think of dropping a letter in the chute of a building: it lands in the letterbox instantly, and you walked away instantly.

7.3 What exactly does a message broker do?

Story box • the sorting office A broker is a postal sorting office. Its jobs: read the address and route the letter correctly; try again tomorrow if nobody was home; deliver in the order things were posted; and photocopy a circular for every household on the list when needed.
Question 9 1 mark • select all that apply

What is the role of the message broker?

  • A. It ensures that the message gets delivered to the correct recipient.
  • B. If the message is undelivered in the first try, it fails and doesn't retry.

Option-by-option reasoning

OptionVerdictWhy
ATRUE Routing to the right recipient is the broker's core job. It is the sorting office reading the address.

9.2 The one-page cheat sheet

The core idea

  • Plain HTTP is client-initiated: the server can never speak first.
  • Pull = the client asks. Push = data arrives unasked.
  • All five techniques are workarounds for that one restriction.

Polling

  • Short polling: fixed repeating interval; server replies immediately, even with nothing. Connection closes each time.
  • Long polling: server holds the connection open and stays silent until it has data, then replies.
  • Polling does not require a persistent connection – each poll is independent.
  • Memory hook: "short reply is instant; long polling makes you wait long."

Server-Sent Events

  • One long-lived HTTP connection; the server streams many events.
  • One way only: server to client. Mime type text/event-stream.
  • Client side is the built-in EventSource object.
  • Needs no task queue, no broker, no new protocol.

WebSockets

  • HTTP handshake with Upgrade: websocket, then switches to ws://.
  • Two way / full duplex, connection stays open.
  • Use when both sides need to send: chat, games, collaborative editing.

Webhooks

  • A user-defined HTTP callback: you register a URL, they POST to it on an event.
  • Push, server-initiated, one way, asynchronous, server-to-server.
  • Content travels in the request body; the response should be a small, immediate 200.
  • Slow response means timeout and retry, which can cause duplicate processing.
  • Can carry JSON, form-encoded or XML data. Can be secured with HMAC signatures, secret tokens, HTTPS and IP allowlists.
  • A receiver can be a trivial Flask route. The connection closes immediately.
  • Often called a reverse API. API = pull (and can push); webhook = push only.

Pub/Sub and brokers

  • Publisher sends to a topic; every subscriber of that topic gets a copy (fan-out).
  • Publisher does not know who or how many subscribers exist – that is decoupling.
  • Communication is asynchronous; delivery to current subscribers is immediate.
  • It is the foundation of event-driven architecture.
  • Broker jobs: correct routing, retries plus a dead letter queue, FIFO order, and fan-out to many recipients when required.
  • Queue = one consumer, "who does this job". Pub/Sub = all subscribers, "who needs to know".

9.4 Practice questions

Cover the answers. If you can do these eight, you have genuinely learned the topic.

P1. A dashboard must show a live share price that changes every second. The browser never sends anything back. Which technique, and why not WebSockets?

P2. Your payment provider POSTs to your webhook URL. Your handler takes 45 seconds because it generates an invoice PDF. Name two things that will go wrong, and the fix.

P3. A client polls every 10 seconds. An event happens 1 second after a poll. What is the worst-case delay before the client learns about it? What would it be with long polling?

P4. Why can a browser tab not be a webhook receiver?

P5. Which of these keeps a connection open: short polling, long polling, SSE, WebSocket, webhook?

P6. One message is published to a topic with 4 subscribers. How many times is it processed? And if it were sent to a point-to-point queue with 4 consumers?

P7. Your webhook URL is public. Anyone can POST fake payment events to it. How do you stop them?

P8. Give one reason to choose SSE over WebSockets, and one reason to choose WebSockets over SSE.

Answers to the practice questions

P1. SSE. The data flows one way only, so a two-way channel would be wasted complexity: WebSockets need protocol support on the server, extra infrastructure configuration, and they lose the free automatic reconnection that EventSource gives you. Use the simplest tool that fits.

P2. (1) The provider times out and marks the delivery as failed. (2) It then retries, so you may process the same payment two or three times and send duplicate invoices. The fix: reply 200 OK immediately, push the PDF job onto a background queue, and make your handler idempotent so a repeated event is harmless.

P3. Polling: worst case about 9 seconds (it must wait for the next scheduled poll). Long polling: essentially zero – the connection is already open and silent, so the server responds the instant the event happens.

P4. A webhook is an incoming HTTP POST, so the receiver needs a publicly reachable URL and a server listening on it. A browser tab has no public address and cannot accept incoming connections. That is why webhooks are server-to-server.

P5. Long polling (holds one request open), SSE and WebSocket (both truly persistent). Short polling and webhooks close the connection immediately.

P6. Topic with 4 subscribers: 4 times, once per subscriber (fan-out). Point-to-point queue with 4 consumers: once – the first consumer to take it removes it, and the other three never see it.

P7. Verify an HMAC signature computed from the body with a shared secret, so a forged POST fails the check. Add HTTPS, a secret token, a timestamp check to block replays, and optionally an IP allowlist. Reject anything that fails.

P8. SSE over WebSocket: it is plain HTTP, so it works through ordinary proxies and firewalls with no special server support, and it reconnects automatically. WebSocket over SSE: the client can send messages too, which SSE simply cannot do.

TermMeaning in one sentence

9.6 Final word

If you remember only six sentences from this whole book
  1. HTTP makes the client speak first; every technique here works around that.
  2. Short polling answers instantly even with nothing; long polling holds the connection open and stays silent.
  3. SSE is one way (a loudspeaker); a WebSocket is two way (a phone call).
  4. A webhook is push, server-initiated, one way, asynchronous, and server-to-server; it closes immediately and needs a fast 200.
  5. An API can pull and push; a webhook only pushes.
  6. Pub/Sub fans one message out to every subscriber of a topic, and a broker routes, retries and works FIFO.
