Part A • Chapter 1Objects, this, and "Who Is Calling Me?" The single most tested idea in this paper. Master this and 6 questions fall over.

1.1 What is an object?

An object in JavaScript is a labelled box. Inside the box you put properties (facts) and methods (actions). You write it with curly braces { }.

const dog = {
  name: 'Bruno',        // property — a fact
  legs: 4,              // property — a fact
  bark: function() {    // method — an action
    console.log('Woof!');
  }
};

dog.name;      // 'Bruno'   → read a property with a dot
dog.bark();    // 'Woof!'   → run a method with a dot and ()
Kid story An object is your school bag. Properties are things inside it (a pencil, a tiffin box). Methods are things the bag can do for you (open the zip). You always reach inside using a dot: bag.pencil.

1.2 The word this means "the box I was called from"

Inside a method, this is a pronoun. It does not mean "the object where the function was written". It means "whatever object was in front of the dot at the moment the function was called."

The Golden Rule of this Look at the call site — the exact line where the function is invoked. Whatever sits immediately to the left of the dot becomes this. If there is no dot, this is undefined (strict mode) or the global object (sloppy mode). 
const a = { name: 'A', who() { console.log(this.name); } };
const b = { name: 'B' };

a.who();            // 'A'  → 'a' is left of the dot
b.who = a.who;    // copy the SAME function into b
b.who();            // 'B'  → now 'b' is left of the dot!

const loose = a.who;
loose();            // undefined → no dot, no owner
Kid story — the microphone A function is a microphone that says "this is my school". The microphone doesn't own a school. Whoever holds the microphone gets named. Hand the mic to Riya → it says "Riya's school". Hand it to Aman → "Aman's school". Same mic, different answer.
So: to find this, find who is holding the mic on the calling line.

1.3 Arrow functions are different (and this is examined)

A normal function function(){} gets a fresh this every time it is called. An arrow function () => {} has no this of its own. It permanently borrows this from the code that surrounds it (its lexical scope), decided where it was written, not where it is called.

Figure 1.1 — Normal function vs Arrow function
Two function types, two completely different this stories.
const team = {
  name: 'Tigers',
  normal: function() { console.log(this.name); },
  arrow:  ()  => { console.log(this.name); }
};
team.normal();  // 'Tigers'  → dot rule works
team.arrow();   // undefined → arrow looked OUTSIDE the object
Trap the examiner sets Statements like "in a regular function this is always the global object" and "in an object method this always refers to that object regardless of how the function is defined" are FALSE. The words always and regardless are the giveaway — this depends on the call, and arrow methods break the object rule.
(This is exactly Question 21.)

Part A • Chapter 2call, apply, bind Three ways to force a function to use a `this` of your choosing.

Sometimes a function lives in object A but you want it to work on object B's data. JavaScript gives three tools for that. All three exist on every function.

Figure 2.1 — The three tools at a glance
call and apply pull the trigger immediately. bind only loads the gun.
Kid story — the borrowed cricket bat Rohit owns a bat (a function). Aman wants to bat.
  • call → "Aman, take the bat and hit right now, here are 2 balls: ball1, ball2." You immediately see the runs scored.
  • apply → identical, but you hand over a basket of balls: [ball1, ball2].
  • bind → "Here is a new bat with Aman's name written on it." Nobody has hit anything yet. No runs. You are holding a bat, not a score. That is why typeof a bound thing is always "function".

2.1 Partial application — bind can pre-fill arguments

This is the part students miss. bind takes the new this first, and then any number of arguments to lock in permanently. Later arguments you pass get appended after them.

function add(a, b) { return a + b; }

const add5 = add.bind(null, 5);   // 'a' is locked to 5 forever
add5(3);   // 8   → 3 slots into 'b'
add5(10);  // 15  → 10 slots into 'b'
The bind argument-slotting recipe
StepWhat to do
1Write the original parameter list: calculate(a, b)
2Fill slots left-to-right with the args given at bind time.
3Fill the remaining slots with the args given at call time.
4Extra args beyond the slots are simply ignored.
Example: f.bind(obj, 4) then f(8) → a=4, b=8.
Trap const g = f.bind(obj, 4); on its own prints nothing. No console output, no side-effects. Students who assume bind executes will get the log order wrong in Q1.

Part A • Chapter 5Classes, the Prototype Chain, instanceof How JavaScript does inheritance — and how to answer chain questions in 20 seconds.

5.1 A class is a blueprint

class BaseComponent {
  constructor(name) { this.name = name; }   // runs on `new`
}
class AdvancedComponent extends BaseComponent {
  constructor(name, role) {
    super(name);        // MUST call parent constructor first
    this.role = role;
  }
}
const comp = new AdvancedComponent('Alice', 'admin');
Kid story — the family tree extends means "my parent is...". super(name) means "Papa, you fill in the parts you know first, then I'll add mine." An object made by new can ask its parent, its grandparent, its great-grandparent... for anything it doesn't have itself. That upward line of relatives is called the prototype chain.

5.2 The chain, drawn once and for all

Figure 5.1 — The prototype chain of comp
One __proto__ = one step up the family tree.
Two rules that answer every chain question
  1. Counting rule. Each .__proto__ is one step up. Step 1 lands on the class you used with new. Step 2 lands on its parent. So comp.__proto__ === AdvancedComponent.prototype is true, and comp.__proto__.__proto__ === BaseComponent.prototype is true.
  2. instanceof rule. It searches the entire chain, not just one level. A child is an instance of itself and every ancestor. So both comp instanceof AdvancedComponent and comp instanceof BaseComponent are true.
Consequence: for a simple extends setup, chain questions are almost always true true true true. (Question 24.)

Part A • Chapter 6Sync vs Async — The Event Loop Kitchen Why "END" gets printed before "A 1" even though it is written last.

6.1 JavaScript has only ONE cook

JavaScript is single-threaded: exactly one line of code runs at a time. So how does it download a file without freezing? It hands slow jobs to the browser and keeps going. When the browser finishes, it puts your callback in a queue and JavaScript picks it up later.

Kid story — the one-cook kitchen One cook (JavaScript) in a kitchen. A customer orders toast (slow). The cook does not stand and stare at the toaster — he puts the bread in, and immediately serves the next customer their water, biscuits, everything quick. Only when all the quick jobs are done does he come back for the toast.
Moral: all the "quick" (synchronous) work in a file finishes first. Every .then() callback is toast — it waits.

Three lanes, strict priority. Memorise the bottom green line.
Exam shortcut for output-order questions Scan the program twice.
Pass 1 — write down every log that is NOT inside a callback. These print first, top to bottom.
Pass 2 — write down the logs inside .then/.catch, in chain order.
Stick the two lists together. Done. (This single trick solves Question 13.)

Part A • Chapter 7Promises — The Complete Rulebook 4 questions in this paper are pure promise-chain tracing. Learn the 6 rules below and you cannot lose a mark.

7.1 A promise is a delivery receipt with 3 states

PENDINGstill working
→
FULFILLEDresolve(value)
or
REJECTEDreject(err) / throw

A promise starts pending. It settles exactly once, into either fulfilled (success, carrying a value) or rejected (failure, carrying a reason). Once settled it can never change.

Kid story — the pizza token You order a pizza and get a token. The token is the promise. Right now it is pending — no pizza yet, but you hold something real that you can plan around. Later either the pizza arrives (fulfilled) or they say "out of cheese" (rejected). You cannot un-deliver a pizza: once settled, settled forever.

7.2 The 6 rules of a chain

Think of .then().catch().then() as a conveyor belt of stations. A parcel travels from station to station. Each station is either a green station (.then) or a red station (.catch). The parcel itself is either green (a value) or red (an error).

#RuleWhat it means in practice
1Green station, green parcel .then runs when the incoming value is a success.
2Green station, red parcel .then is SKIPPED entirely. The error jumps over it, untouched, looking for a .catch.
3Red station, red parcel .catch runs and catches the error.
4Red station, green parcel .catch is SKIPPED. Nothing was broken, so there is nothing to fix.
5RETURN turns the parcel green Whatever a handler returns becomes the success value of the next station. This is true for .catch too — a catch that returns a value heals the chain and the rest continues normally.
6THROW turns the parcel red Whatever a handler throws becomes the rejection reason of the next station.
Rule 5 is the most examined idea on this page Students believe "once there is an error, everything after it dies." Wrong. A .catch that returns something is like a hospital: the parcel walks out healthy, and every following .then runs as if nothing happened.

7.3 Two more rules you need for this paper

Rule 7: console.log passed bare is still a function call

.then(console.log) means "when the value arrives, call console.log with it". It is identical to .then(v => console.log(v)). Do not read it as "nothing happens".

Rule 8: returning a promise makes the chain WAIT (this is called adoption)

If a handler returns a promise instead of a plain value, the chain does not move on with the promise object — it pauses until that inner promise settles, then continues with the inner promise's value. This is what makes setTimeout-based delays work inside chains.

const processString = (str) => {
  return new Promise((resolve) => {
    setTimeout(() => resolve(str.toUpperCase()), 100);
  });
};
Promise.resolve('hello')
  .then(processString)              // returns a PROMISE → chain WAITS 100ms
  .then(r => r + ' WORLD')        // receives 'HELLO', not a Promise object
  .then(console.log);
HELLO WORLD
Trap Students answer [object Promise] WORLD or hello WORLD. Both wrong. Rule 8 unwraps the promise (so you get the uppercased string), and the delay is invisible in the output. (Question 19.)

Useful combinators (know the names)

MethodBehaviour
Promise.all([...])Waits for all. Rejects immediately if any one rejects. All-or-nothing.
Promise.allSettled([...])Waits for all, never rejects. Gives you a status for each.
Promise.race([...])Settles with the first one to settle, success or failure.
Promise.any([...])Settles with the first success; ignores failures.
.finally(fn)Always runs. Does not change the value passing through.

Part A • Chapter 8fetch — and the 404 Surprise The single most common real-world JavaScript bug, and it is a favourite exam question.

8.1 The surprising rule

The rule, in one line fetch() only rejects when the request never got an answer (no network, DNS failure, CORS blocked, request aborted).
If the server answered at all — even with 404, 401, or 500 — the promise FULFILLS. You must check response.ok yourself.
Kid story — the postman You send a letter asking for a book. The postman's only job is to bring back a reply envelope.
  • The library replies "here is your book" → postman delivered. Success.
  • The library replies "404 — no such book" → the postman still delivered an envelope! His job succeeded. fetch still resolves. The bad news is inside the envelope.
  • There is a flood and the postman never comes back → now it is a failure. fetch rejects.
fetch judges the postman, not the message.

Part A • Chapter 11computed vs methods vs watch Caching is the whole story. Five questions live here.

11.1 The three tools

computed
A value derived from other data. CACHED. Re-runs only when one of the reactive things it read changes. Used in the template like a property (no brackets): {{ total }}
methods
A plain function. NOT cached. Runs every single time it appears in a re-render, or whenever you call it. Called with brackets: {{ total() }}
watch
"When X changes, do something." Used for side-effects: fetch data, save to storage, update another variable. Returns nothing useful.
Kid story — the shopkeeper's calculator A customer keeps asking "what's my total?"
  • method = a lazy shopkeeper who re-adds every item from scratch, every single time you ask. Ask 10 times → 10 full calculations.
  • computed = a smart shopkeeper who writes the total on a sticky note. Ask 10 times → he reads the note 10 times, 1 calculation. He only tears up the note and recalculates if you actually add or remove an item.
  • watch = a bell on the door: "whenever a new customer walks in, ring the bell and SMS the manager." It isn't producing a value; it's reacting to a change.

11.2 How the cache decides to expire (the "dirty flag")

Figure 11.1 — Dependency tracking for expensive()

The rule that decides every caching question A computed property re-runs only if a reactive value it actually READ inside its own body has changed.
Changing any other piece of data — even if it causes the component to re-render — will not re-run it. The template simply reads the cached value again.

So the test is mechanical: list the this.xxx names inside the computed function. That list, and nothing else, is its trigger list.
Trap Date.now(), Math.random(), and localStorage are not reactive. A computed property that uses them will never update on its own. That is why "when Date.now() changes" is always a wrong option.

11.3 When to use a watcher instead

  '$route.params.id': function(newId, oldId) {
    this.userId = newId;      // side-effect: copy into data

Decision guide Do you want a value to display? → computed.
Do you want to DO something (fetch, save, assign to another variable)? → watch.
Do you need it to run on a click/event? → methods.
Trap Data properties (things in data()) are dumb boxes. They do not recalculate themselves. If a variable in data should change when something else changes, somebody must assign to it — that somebody is a watcher or a method. This is precisely why the watcher in Questions 29, 30 and 32 is needed.

Part A • Chapter 12Components: Props Down, Events Up The one-way data flow law, and $emit.

12.1 The law of one-way data flow

The law Data flows DOWN from parent to child using props.
Events flow UP from child to parent using $emit.
A child may never reach up and change the parent's state directly. It can only request a change by shouting an event; the parent decides whether to act.
Kid story — pocket money Papa (parent) gives you ₹50 (a prop). You cannot open Papa's wallet and take more — that would be chaos, and nobody would know who spent what. What you can do is shout "Papa, I need 20 more!" (that is $emit). Papa hears it and decides. The money always moves one way, and the shouting goes the other way.

12.2 The four facts about $emit

StatementVerdictReason
Parent can listen with @updateTRUE The first argument to $emit is the event name, so @update (short for v-on:update) is exactly how you subscribe.
Parent receives the payload via $eventTRUE Inside an inline handler, the emitted value is available as $event. (With a method handler it arrives as the first parameter.)

  • D: Date.now() is a plain function call, not reactive at all. Vue has no way to know time has passed. Even if the computed did call Date.now(), it would never re-run on its own — the cached value would be frozen forever.
Answer to Q27 Option C — either this.a or this.b changes Rule: only the reactive values read inside the body are triggers.

What are the benefits of computed caching in Vue?

Question 29 — What happens when the user clicks "User 2" after initially opening "User 1"?

  • A The route changes to /user/2 but the userId in data does not update
  • B The watcher updates userId to "2", and the <p> displays it instantly  ✓ CORRECT
  • C The router-view still shows User 1 because watchers don't re-render components
  • D An error occurs because $route.params.id cannot be watched
Chain of events on the click
  1. Click the <router-link to="/user/2"> → the URL becomes /user/2.
  2. $route.params.id changes from "1" to "2". Because $route is reactive, Vue notices.
  3. The watcher fires with newId = "2" and executes this.userId = "2".
  4. userId is a reactive data property, so assigning to it triggers a re-render of the <p>, which now shows "Current userId: 2".
  5. Independently, the User component's template re-reads $route.params.id and shows "User component loaded with ID: 2".
Both parts of the page are correct and up to date. That is option B.

Why the others fail:

  • A: would be true only if the watcher did not exist. It does exist, and its entire job is to perform that update. (This is the link to Q30.)
  • C: confuses two mechanisms. The router-view updates because $route is reactive, not because of the watcher. The watcher's job is only to sync the data property. Nothing here keeps User 1 on screen.
  • D: watching a nested string path is fully supported — '$route.params.id' as a quoted key is standard, documented Vue syntax. No error.
Answer to Q29 Option B userId becomes "2" (a string, since URL params are always strings) and renders immediately.

Question 30 — Why is the watcher on $route.params.id necessary?

Evaluate A and B independently, then decide
 Is it true on its own?
ATRUE. userId is initialised to null and nothing else in the whole app assigns to it. Delete the watcher and the <p> would show "Current userId: " forever, no matter how much you navigate. So the watcher is what makes it change.

Common code. An e-commerce product list filtered by the route parameter /products/:category.

const ProductList = {
  template: `<div>{{ filteredProducts }}</div>`,   // ← LOOK CAREFULLY at this
  data() {
    return {
      allProducts: [
        { id: 1, name: 'Laptop', category: 'electronics' },
        { id: 2, name: 'Novel',  category: 'books' },
        { id: 3, name: 'Phone',  category: 'electronics' }
      ],
      displayedProducts: null
    };
  },
  computed: {
    filteredProducts() {
      return this.allProducts.filter(p => p.category === this.$route.params.category);
    }
  },
  watch: {
    '$route.params.category': function(newCategory) {
      this.displayedProducts = this.filteredProducts;
    }
  }
};
Read the template before anything else — this is the whole trick The template renders {{ filteredProducts }} — the computed property.
It does NOT render displayedProducts. That data property is written to by the watcher but is never displayed anywhere.
So every option that reasons about displayedProducts being null on screen is a distractor.

Question 31 — What will be rendered when the user first navigates to /products/electronics?

  • A An empty array because displayedProducts is initialized as null
  • B All three products because the watch handler hasn't been triggered yet
  • C Only the Laptop and Phone (both electronics)  ✓ CORRECT
  • D The data will show an error because the category doesn't exist in the array
Step-by-step
  1. The template needs filteredProducts, so Vue evaluates that computed getter for the first time.
  2. Inside it, this.$route.params.category is read. On the very first render the route is already resolved, so this is 'electronics'. (Computed properties are evaluated lazily during render, at which point $route is available.)
  3. The filter runs over allProducts:

    1Laptop'electronics' === 'electronics' → trueKEPT

    3Phone'electronics' === 'electronics' → trueKEPT

Why the others fail:

  • A: the trap. It reasons about the wrong variable. displayedProducts is null, correct — but it is not in the template.
  • B: the watcher's absence is irrelevant. The computed does the filtering, and it filters correctly the very first time. Nothing would ever show all three products.
  • D: Array.prototype.filter never errors on a non-matching value; it just returns fewer items (or []). Here 'electronics' does exist anyway.

Question 32 — When the user navigates from /products/electronics to /products/books, what will happen and why?

  • A The computed property will not update because it's being used in a watch handler
  • B The computed property will automatically re-evaluate because the route parameter dependency changed (true, but incomplete — see below)
  • C The displayedProducts variable will update, but the computed property will display stale data
  • D Both the computed property and displayedProducts will update to show books  ✓ CORRECT
Trace both mechanisms — they both fire
#EventConsequence
1URL param changes
electronics → books		 $route.params.category is reactive, so Vue registers the change.
2Computed invalidated filteredProducts read this.$route.params.category, so that is one of its dependencies. The cache is marked dirty.
3Watcher fires The handler runs and executes this.displayedProducts = this.filteredProducts. Reading this.filteredProducts here forces the dirty computed to recompute now, returning the books list. ⇒ displayedProducts = [{ id:2, Novel, books }].
4Re-render The template reads {{ filteredProducts }} and gets the fresh books array. The screen shows the Novel.
Net effect: BOTH the computed and displayedProducts now hold the books data. That is option D.
Why D rather than B? Statement B is factually true — it correctly describes the mechanism (the computed re-evaluates because a dependency changed). But the question asks what will happen, and B tells only half the story: it omits that the watcher also runs and updates displayedProducts. D describes the complete outcome and contradicts nothing.
How to answer safely: if your exam allows only one choice, pick the option that is true and most complete — D. Make sure you can also state B's reasoning aloud, because B is the why behind D.

Why A and C are definitely wrong:

  • A: using a computed inside a watch handler has no effect on its reactivity. Reading a computed never disables its dependency tracking. Vue does not care who reads it.
  • C: exactly inverted. A computed can never be stale — it is invalidated automatically. It is data properties like displayedProducts that go stale if nobody updates them. C describes the opposite of how Vue works.
Answer to Q32 Option D — both update to show books Computed re-evaluates automatically (dependency changed) and the watcher copies the fresh result into displayedProducts.

C.3 Night-before one-page sheet

JAVASCRIPT
  • this = left of the dot, at call time.
  • arrow = this from outside, fixed forever.
  • call(this, a, b) → runs now.
  • apply(this, [a, b]) → runs now, Array.
  • bind(this, a) → returns a function, pre-fills left to right.
  • objects copy by reference. Dot = mutate (sticks). Bare = re-assign (doesn't).
  • map same length • filter same or fewer • reduce one value.
  • __proto__ = 1 hop. instanceof = whole chain.
ASYNC
  • Order: sync → microtasks (.then) → setTimeout.
  • .then skipped when an error is flowing.
  • .catch skipped when a value is flowing.
  • return → next parcel is green (healed).
  • throw → next parcel is red.
  • Return a Promise → chain waits & unwraps.
  • fetch: 404/500 → resolves, ok=false. Only network failure rejects.
STORAGE
  • localStorage = forever, shared across tabs.
  • sessionStorage = dies with the tab.
  • cookie = small, auto-sent to the server.
  • Everything stored is a string.
  • getItem missing → null.
SECURITY
  • Passwords → bcrypt / Argon2 (one-way, salted, slow).
  • XSS → escape output; {{ }} safe, v-html dangerous.
  • CSRF → SameSite=Strict + token.
  • Secure = HTTPS only.
  • HttpOnly = JS can't read it.
  • Strict > Lax > None (None = no protection).
VUE
  • v-if = removes from DOM, hooks re-run.
  • v-show = display:none, no re-mount.
  • computed = cached, sync, re-runs only if a value it read changed.
  • method = every render, never cached.
  • watch = do a side-effect on change; not on first load.
  • props down, events up. $emit('name', payload), listen @name, read $event.
  • $emit is a Vue event, not a DOM event.
VUE ROUTER
  • Strip host/# → that's the path.
  • Child renders inside parent's <router-view>. Output = parent + child.
  • path: "" = default child, only when nothing is left over.
  • Same pattern, new param → instance reused, hooks don't re-run → stale data.
  • Auto-fresh: {{ $route.params.x }} and computed reading it.
  • Goes stale: data vars and anything fetched in created.
  • Fix = watcher (immediate: true) or :key on router-view.
VUEX
  • state = single source of truth.
  • mutations = the ONLY writers, synchronous.
  • actions = async, then commit.
  • getters = read-only, cached.
  • dispatch → action → commit → mutation → state.
REDIS / CELERY / WEBHOOKS / GIT
  • Redis = in-memory data structure store; cache, broker, pub/sub. No SQL.
  • Stores strings, hashes, lists, sets, sorted sets.
  • Celery: Redis = broker + result backend. Workers execute and retry.
  • Webhook = HTTP POST, async. No order guarantee, no auto retry.
  • Git: the branch you stand on receives. On appdev2 → git merge main.
