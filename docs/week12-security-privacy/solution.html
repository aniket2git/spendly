Part 1 • Question 1Denial of Service

Story box • the blocked shop door A small shop can serve about ten customers at a time. A rival hires five hundred people to crowd into the doorway, all shouting questions, none of them buying anything.

The rival has not stolen anything. He has not broken the till or read the account books. But real customers cannot get in, so the shop might as well be closed. The damage is unavailability.

That is a Denial of Service attack. Notice what it is not: it is not about breaking in.
Definition box • DoS A Denial of Service (DoS) attack aims to make a service unavailable to its legitimate users. The usual method is to send a huge, continuous volume of requests so the server exhausts its resources – connections, memory, CPU, bandwidth – and slows to a halt or crashes.

For DoS the answer is always the ordinary users. Any option that says the attack blocks hackers has the arrow backwards.

Part 2 • Question 2Passwords, and what NIST actually says

Most of what people "know" about passwords is out of date. The modern reference is NIST Special Publication 800-63B, and it overturned several rules that older websites still enforce.

2.1 Length beats complexity

Story box • the bicycle lock Two number locks. One has 4 wheels but each wheel has letters, digits and symbols. The other has 12 wheels with digits only.

A thief trying every combination has far more work on the 12-wheel lock, even though each individual wheel is simpler. Adding wheels multiplies the work; making one wheel fancier only adds a little.

Passwords behave identically. Xk#7q looks impressive and is weak. correct horse battery staple looks simple and is enormously stronger – and you can actually remember it.

2.2 Salting and hashing

Story box • the one-way mincer A hash is a mincing machine. Put a password in, get mince out. You can always mince the same password and get the same mince, so you can check a login – but you can never turn mince back into meat. That is why the server never needs to store your actual password.

Problem: everybody who picks password123 produces identical mince, so one lookup table cracks thousands of accounts at once.

Solution: before mincing, add a unique pinch of salt for each user – a random value stored alongside. Now two people with the same password produce completely different mince, and precomputed tables are useless.

2.3 The NIST 800-63B rules, and the myths it retired

Question 2 1 mark • single correct

Which of the following does not come under the guidelines released by NIST Special Publications 800-63B?

  • A. The users should not be asked to reset their passwords after every certain period.
  • B. The number of attempts to log in into an account should be made limited before locking the amount.
  • C. The passwords should be hash with at least a 32-bit salt data before storing them in the database.
  • D. The users should choose a complex password over a lengthy password, as a complex password can be easily decrypted compared to a lengthy password.
Read the instruction twice The question asks which one is not a guideline. So three options are genuine NIST advice, and you must tick the odd one out.

Option-by-option reasoning

OptionIs it NIST advice?Why
AYES This is one of the most famous changes NIST made. Forced periodic resets are discouraged, because users respond by making tiny predictable edits (Summer2023 becomes Summer2024), which reduces security rather than improving it. Reset only when there is evidence of compromise.
BYES Limiting failed login attempts is standard NIST guidance – it is what stops brute-force and credential-stuffing attacks. (The phrase "locking the amount" is a typo for "locking the account".)
CYES Salted hashing before storage is required, and NIST specifies the salt shall be at least 32 bits in length. Figure 2.2. The specific number in this option is what makes it identifiable as genuine NIST wording.
DNO
the answer		 Wrong twice over.
(1) NIST treats length as the primary strength factor, so preferring complexity over length is the opposite of the guidance.
(2) The reason given is nonsense: passwords are hashed, not encrypted, so nothing about them is "decrypted" – and even if it were, a complex password being easier to break makes no sense as an argument for choosing it.
Answer to Question 2 Option D
Length beats complexity, and passwords are hashed rather than decrypted. Matches your selection.
A shortcut for this question type You did not even need to know NIST to answer it. Option D contains a factual impossibility – "a complex password can be easily decrypted" – and an option that is internally illogical cannot be anybody's official guideline. When one option contains a broken claim, it is almost always the answer.

Part 3 • Question 10Origins, the same-origin policy and CORS

Three of the ten questions touch CORS, so the idea of an origin is worth getting exactly right. It is a precise, mechanical definition – no judgement involved.

3.1 What is an origin?

Story box • the postal address Two letters come from the "same address" only if the street, the house number and the city all match. If any one of the three differs, it is a different address – even if the family name is the same.

An origin is exactly that kind of triple. Three parts must all match: the scheme, the host and the port. Anything after that – the path, the query string, the fragment – is irrelevant.

3.2 Same origin or not? Worked examples

Compare each pair against http://example.com, applying the three-part test:

The other URLSame origin?Reason
http://example.com/profileYES Scheme, host and port all identical. Only the path differs, and paths are ignored. This is Q10 option D.
http://example.com/a/b?x=1YES Deeper path and a query string – still irrelevant.
http://api.example.comNO Different host. A subdomain is a different host, so a different origin. This is Q10 option C, which is therefore false.
https://example.comNO Different scheme (http vs https). This one surprises people.
http://example.com:8080NO Different port (8080 vs the default 80).
http://example.orgNO Different host entirely.
Trap box • the two that catch everyone 1. Subdomains are NOT the same origin. example.com and api.example.com are different origins, even though they share a parent domain.
2. Paths never matter. example.com and example.com/profile are the same origin.

Notice this is the opposite of how cookies behave. A cookie with domain=example.com is shared with api.example.com, but they are still different origins. Cookie scope and origin are two different rules – do not merge them.

3.3 The same-origin policy, and how CORS relaxes it

Story box • the locked staff room By default, a browser is very suspicious: a page from one origin may not read data from another origin. Otherwise any dodgy site you visited could quietly read your webmail in another tab.

But some sharing is legitimate. So the receiving server is allowed to put up a notice saying "these particular visitors may come in, using these particular methods". CORS is that notice system. The default remains deny; CORS is how a server chooses to permit specific origins.
Question 10 1 mark • select all that apply

Which of the following statements is true?

  • A. CORS prevents browsers from loading data from different origins by default.
  • B. CORS prevents browsers from loading data from the same origin by default.
  • C. http://example.com and http://api.example.com have the same origin.
  • D. http://example.com and http://example.com/profile have the same origin.

Option-by-option reasoning

OptionVerdictWhy
ATRUE The default posture for cross-origin reads is deny. A browser will not hand another origin's data to your JavaScript unless that server explicitly permits it. Left panel of Figure 3.2.
BFALSE Nothing blocks same-origin requests – a page loading its own data is the normal, always-allowed case. A and B are opposites, so exactly one is right, and this is the wrong one.
CFALSE Different host, therefore a different origin. api.example.com is a subdomain, and a subdomain is a separate host. This is precisely why a front end at example.com calling an API at api.example.com needs CORS headers.
DTRUE Same scheme (http), same host (example.com), same port (80). Only the path differs, and the path is not part of an origin. Figure 3.1.
Answer to Question 10 A and D
Cross-origin reads are denied by default, and paths do not affect the origin. Matches your selection.
A precision note on option A, so a nitpicker cannot catch you Strictly speaking, the rule that blocks cross-origin access is called the same-origin policy, and CORS is the mechanism that lets a server relax it. So a purist would say "the same-origin policy prevents it; CORS permits it".

Option A is still the intended and defensible answer, because the two form one system whose default is deny: without a CORS header, the data is not delivered. And option B, its only competitor, is plainly false. If you ever have to write this in a long answer, use the precise version: "the same-origin policy blocks cross-origin reads by default; CORS is how a server opts in to allowing them."

Part 4 • Question 4The fetch API in detail

fetch is how JavaScript makes HTTP requests. Two of the questions test its default settings, so let us look at the options object properly.

4.1 The three modes, and what "opaque" means

Story box • the sealed envelope You ask a courier to collect a document from a stranger's office. Three possible arrangements:

cors – the courier may collect it, but only if the office has your name on its approved list. If it does, you can open and read the document.

no-cors – the courier collects it and hands you a sealed envelope you are not allowed to open. You know delivery happened; you cannot read a single word. That sealed envelope is an opaque response.

same-origin – the courier refuses to leave your own building at all.

Part 5 • Question 5XSS: Cross-Site Scripting

Story box • the poisoned notice board A school notice board lets any student pin up a message, and the office copies every message onto the school website exactly as written.

A mischievous student pins up a note that is not really a message at all – it is an instruction: "whoever reads this, hand over your lunch money". Because the office copies it blindly, every visitor's browser now obeys the instruction, believing it came from the school.

That is XSS: the attacker gets their own script to run inside someone else's page, so the browser trusts it as if the site had written it.
Definition box • XSS Cross-Site Scripting (XSS) is an exploit in which an attacker injects malicious client-side scripts into a web page viewed by other users. The root cause is that the application takes user input and puts it into a page without validating or escaping it.

5.1 How XSS is prevented

Part 6 • Questions 6 and 7CSRF, and the token that stops it

Story box • the signed blank cheque You are logged into your bank in one tab. Being logged in means your browser holds a session cookie, and it attaches that cookie automatically to every request going to the bank – without asking you.

Now you open a different site showing a funny cat picture. Hidden in that page is a form that quietly submits a transfer request to your bank. Your browser, being helpfully obedient, attaches your bank cookie to it.

The bank sees a properly authenticated request from you and carries it out. You never clicked anything about a transfer. The attacker never needed your password – they borrowed your logged-in browser.
Definition box • CSRF Cross-Site Request Forgery (CSRF) makes an authenticated user's browser send a request the user did not intend. It works by exploiting the trust that exists between the application and its authenticated users: the application cannot tell a forged request apart from a genuine one generated by its own user interface.

Trap box • the classic mix-up of the two "trust" sentences Two similar-sounding sentences float around, and swapping them is a common exam error:
  • XSS abuses the user's trust in the website – the victim's browser believes the injected script came from the site.
  • CSRF abuses the website's trust in the user – the server believes the forged request came from its logged-in user.
One sentence points each way. Draw the arrow before you answer.

6.1 The CSRF token

Story box • the secret word of the day The bank fixes its problem like this. Every time it hands you a genuine transfer form, it also writes a fresh secret word on that form – and remembers the word for your session. A transfer is accepted only if the correct word comes back with it.

The attacker's hidden form cannot contain the word: they never received your form, and the same-origin policy stops their JavaScript from reading it out of your page. Their forged request arrives with no word, or the wrong one, and is rejected.

That secret word is the CSRF token. Note who writes it: the server. A token the client invented would prove nothing, because the attacker is also a client.

6.2 How the token travels back

Option C of Question 7 mentions a custom header, so it is worth knowing both routes:

<!-- ROUTE 1: as a hidden form field -->
<form method="POST">
  <input type="hidden" name="csrf_token" value="a9f3...">
  <button>Transfer</button>
</form>

// ROUTE 2: as a CUSTOM HEADER, which is what AJAX and fetch normally use
fetch('/transfer', {
  method: 'POST',
  headers: { 'X-CSRFToken': token },   // a custom header
  body: JSON.stringify(data)
})
Why a custom header is itself a small defence A plain HTML form cannot set custom headers. So the moment a request carries X-CSRFToken, it must have come from JavaScript – and cross-origin JavaScript adding a custom header triggers a CORS preflight, which the attacker's origin will fail. This is one of the places where CORS and CSRF protection genuinely overlap, and it matters for Part 7.

Part 7 • Question 3CORS and CSRF together

Question 3 puts CORS, CSRF and fetch in one question. You have already met all three ideas, so this part just joins them up.

7.1 How CORS helps against CSRF, and where it stops helping

Story box • the guard who checks some doors A building hires a guard who checks ID at the side entrance used by delivery vans, but the front door is a public entrance that anyone may walk through.

The guard is genuinely useful – the side entrance is now protected. But you would be foolish to sack the receptionist inside, because the front door is still open.

CORS is that guard. It blocks a whole class of cross-origin attacks, so it genuinely can be used to help avoid CSRF. But it does not cover every route in, which is why the CSRF token (the receptionist) stays.
The precise position, worth understanding properly Option B of Q3 says CORS "can be used to avoid CSRF vulnerability". Read the wording carefully: it says can be used to, not is sufficient to. That is a fair claim – a correctly configured CORS policy is one of the recognised layers of CSRF protection, and it is what makes the custom-header technique in Part 6 work.

What would be false is a stronger sentence such as "CORS completely prevents CSRF" or "with CORS you do not need a CSRF token". If you meet one of those in the end term, mark it wrong – a plain cross-origin form POST is not blocked by CORS.

Part 8 • Questions 8 and 9Privacy, security, and quiet data leaks

The last two questions leave attacks behind and ask about two words people use interchangeably but which mean different things.

8.1 Privacy is not the same as security

Story box • the diary and the cupboard Privacy is the question: which of my secrets am I willing to tell you at all? It is about the information itself and the person's wishes.

Security is the question: how strong is the cupboard you keep my diary in? It is about the mechanisms protecting whatever you were given.

You can have one without the other. A bank with excellent locks that then sells your transaction history to advertisers is secure but not private. A company that sincerely promises never to share your data but stores it in a plain text file on a public server is private in intent but not secure. You need both.

8.2 Leaking data without handing over the data

Story box • the shop that guessed A shop never tells anyone what you bought. Then it starts posting baby-product offers to your house. Your relatives see the envelopes and work out that somebody is expecting a baby.

The shop never published your purchase list. But its recommendations revealed the conclusion drawn from that list – which was the sensitive part all along.

That is an indirect leak: the raw data stayed secret, and the information still escaped.

9.2 The whole week on one page

9.3 The one-page cheat sheet

Denial of Service

  • Goal: make a service unavailable to legitimate users. Not about stealing data.
  • Usual method: continuous bulk requests until resources are exhausted.
  • DDoS = Distributed: many machines (a botnet) at once, much harder to block.
  • Defences: rate limiting, filtering, autoscaling, CDN or scrubbing services.

Passwords and NIST SP 800-63B

  • Length beats complexity. Minimum 8 characters, allow up to 64, allow spaces and paste.
  • Salted, slow hashing before storage; the salt must be at least 32 bits.
  • Limit failed login attempts to stop brute force and credential stuffing.
  • Check new passwords against known breached password lists.
  • Do not force periodic resets, and do not demand symbols and mixed case.
  • Passwords are hashed, not encrypted – there is no "decrypting" a password.

Origins and CORS

  • Origin = scheme + host + port. All three must match; the path is irrelevant.
  • example.com and example.com/profile: same origin.
  • example.com and api.example.com: different origins (subdomain = different host).
  • Also different: http vs https, and :80 vs :8080.
  • Cross-origin reads are denied by default; the receiving server opts in with Access-Control-Allow-Origin and Access-Control-Allow-Methods.
  • Precise wording: the same-origin policy blocks, CORS is how a server relaxes it.

The fetch API

  • Defaults: method GET, mode cors, credentials same-origin.
  • mode: 'no-cors' gives an opaque response: status 0, null body, empty headers, and the method is limited to GET, HEAD or POST.
  • credentials controls whether cookies are sent: omit / same-origin / include.

XSS and CSRF

  • XSS: attacker injects client-side scripts into a page. Cause: input not validated or escaped. Abuses the user's trust in the site.
  • XSS defences: escape output, validate input, CSP, HttpOnly cookies. Not a CSRF token.
  • CSRF: a forged request rides on the victim's automatically attached cookie. Abuses the site's trust in the user. The server cannot distinguish forged from genuine.
  • CSRF token: generated by the server, tied to the session, returned as a hidden form field or a custom header such as X-CSRFToken.
  • CORS helps against CSRF but is not sufficient: a plain cross-origin form POST is still allowed.

Privacy and data leaks

  • Privacy: which personal data is collected and shared, and the user's consent.
  • Security: how the data is stored, transmitted and access-controlled.
  • Direct leak: the actual value escapes (password leak, database dump).
  • Indirect leak: the value stays hidden but is inferred – recommendations based on behaviour, "people you may know", differing error messages, response timing.

9.5 Practice questions

Cover the answers. If you can do these eight, you have genuinely learned this week.

P1. Are https://shop.example.com and https://example.com the same origin? What about https://shop.example.com/cart and https://shop.example.com/pay?id=2?

P2. An attacker successfully performs XSS on your site. Explain why your CSRF token no longer protects you.

P3. Your site forces users to change passwords every 30 days and requires a symbol. Which two NIST 800-63B recommendations are you going against, and what should you do instead?

P4. You run fetch('/api/users') with no options. What HTTP method is used, what mode, and will your session cookie be sent?

P5. Why does a CSRF token have to be generated by the server rather than the client?

P6. A login form replies "no account with that email" for unknown emails and "incorrect password" for known ones. What kind of leak is this, and how would you fix it?

P7. You fetch a cross-origin image with mode: 'no-cors'. What can your JavaScript read from the response, and which methods could you have used?

P8. A company encrypts all user data at rest, uses HTTPS everywhere, and then sells aggregated user location histories to advertisers. Is this a security failure, a privacy failure, or both?

Answers to the practice questions

P1. Not the same origin – shop.example.com and example.com are different hosts. The second pair are the same origin: identical scheme, host and port, and paths and query strings are ignored.

P2. Because the attacker's script is now running inside your page, on your origin. It can simply read the CSRF token out of the DOM (or fetch a fresh page and parse it) and include it in a forged request. The same-origin policy no longer helps, since the script is same-origin. This is why XSS is considered the more severe bug: it defeats CSRF protection.

P3. You are going against (1) do not force periodic resets – users respond with predictable edits like Pass1 to Pass2; and (2) do not impose composition rules such as mandatory symbols. Instead: allow long passphrases up to 64 characters, check against breached password lists, throttle failed logins, and reset only on evidence of compromise.

P4. Method GET, mode cors, and yes the cookie is sent – because /api/users is a relative, same-origin URL and the default credentials value is same-origin. (It would not be sent to a different origin unless you set credentials: 'include'.)

P5. Because the attacker is also a client. If clients generated their own tokens, the attacker would generate a valid-looking one and the defence would be worthless. The token works only because the server creates it, remembers it against your session, and can therefore verify that the request came from a page it served.

P6. An indirect leak – the different messages reveal which email addresses are registered, without ever leaking a password. It enables account enumeration. Fix: return a single identical message ("invalid email or password") for both cases, and keep the response time similar so timing does not leak the answer either.

P7. You can read essentially nothing: the response is opaque, with status 0, a null body and empty headers. You can tell the request completed and you can display the image, but you cannot inspect it. Only GET, HEAD and POST were available in that mode.

P8. A privacy failure, not a security failure. The security mechanisms are working correctly – the data is protected from outsiders. The problem is what the company itself chooses to do with data users did not expect to be sold. This is exactly why the two words are not interchangeable.

9.7 Final word

If you remember only seven sentences from this whole book
  1. DoS attacks availability – it locks out real users, it does not steal.
  2. NIST says length beats complexity, salt with at least 32 bits, throttle logins, and do not force periodic resets.
  3. Origin = scheme + host + port. Subdomains differ; paths do not matter.
  4. Cross-origin reads are denied by default; CORS is how a server names the origins and methods it accepts.
  5. fetch defaults: GET, cors, same-origin credentials. no-cors gives an opaque response limited to GET, HEAD and POST.
  6. XSS abuses the user's trust in the site (fix: escape and validate). CSRF abuses the site's trust in the user (fix: a server-generated token).
  7. Privacy is which data you share; security is how it is protected. And data can leak indirectly, by inference.
