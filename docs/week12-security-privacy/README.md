## The ideas that carry the most marks

**XSS and CSRF abuse trust in opposite directions.** This single sentence pair prevents most
mistakes in this topic:

- **XSS** abuses the **user's trust in the site** — the victim's browser believes the injected
  script came from the site. Fix: **escape output, validate input**, CSP, HttpOnly cookies.
- **CSRF** abuses the **site's trust in the user** — the server believes the forged request came
  from its logged-in user. Fix: **server-generated CSRF token**, SameSite cookies, Origin checks.

That's why Q5 option C is false: a CSRF token is the wrong defence for XSS. Worse, it's useless
against it — a script running inside your page can simply **read the token out of the DOM**.
XSS defeats CSRF protection, not the other way round.

**Origin = scheme + host + port.** All three must match; the path is irrelevant.

| Compared with `http://example.com` | Same origin? | Why |
|---|---|---|
| `http://example.com/profile` | **yes** | only the path differs, and paths are ignored |
| `http://api.example.com` | **no** | subdomain = different host |
| `https://example.com` | **no** | different scheme |
| `http://example.com:8080` | **no** | different port |

Note this is the **opposite** of cookie scoping: a cookie with `domain=example.com` *is* shared
with `api.example.com`, yet they remain different **origins**. Two different rules — don't merge
them.

**NIST 800-63B overturned the folklore.** Length is the primary strength factor (min 8, permit
64), salt with **at least 32 bits**, throttle failed logins, check against breach lists. It
**does not** recommend forced periodic resets or mandatory symbols. Option D of Q2 also contains
a factual impossibility — passwords are **hashed, not encrypted**, so nothing about them is
"decrypted".

**fetch defaults:** method **GET**, mode **cors**, credentials **same-origin**. `mode: 'no-cors'`
yields an **opaque** response (status 0, null body, empty headers) and restricts you to
**GET, HEAD or POST**.

**Privacy ≠ security.** Privacy is **which** data is collected and shared; security is **how**
it's protected. A company with perfect encryption that sells your location history has a privacy
failure, not a security one.

**Direct vs indirect leak.** Ask: did the attacker *receive* the value, or *work it out*?
Received = direct (password leak). Inferred = indirect (recommendations, "people you may know",
differing error messages, response timing).
