Part 1 • FoundationsThe internet in slow motion

Before we can answer a single question, we must be sure about one thing: what actually happens when a web page "loads"? Let us slow it down 1000 times.

Story box • the restaurant You walk into a restaurant and sit down. You are the customer. You call the waiter and say "one dosa please". That sentence is your order. The waiter walks to the kitchen, the cook makes the dosa, and the waiter brings the plate back to your table. That plate is the reply.

The whole internet works exactly like this. Nothing more.
  • You (the customer) = the browser, also called the client. Chrome, Firefox, Safari.
  • The kitchen = the server. A computer somewhere that knows how to make things.
  • Your order = a request.
  • The plate that comes back = a response.
Definition box A client sends a request to a server. The server does some work and sends back a response. The server never speaks first. This ask-then-answer pattern is called the request-response cycle.

1.1 What is a web address really saying?

In the assignment you see the address http://127.0.0.1:5000/profile. It looks scary. It is just four pieces of information, like a postal address.

Story box • the building 127.0.0.1 is the building (your own house). 5000 is the door number of one particular office in that building. /profile is the desk inside that office. Change the desk and a different person answers you.

1.2 What is Flask?

Flask is a small Python toolkit that turns your Python file into a kitchen that can answer orders. You write ordinary Python functions, and you stick a label on each function saying "call me when somebody asks for this address".

# the smallest possible Flask app
from flask import Flask        # borrow the toolkit

app = Flask(__name__)            # create the kitchen

@app.route('/')                   # the LABEL: "when someone asks for /  ..."
def home():                        # ... run this function
    return "Hello!"               # and send this back as the response

if __name__ == "__main__":
    app.run()                      # open the kitchen, start listening
Definition box • three words to keep
  • Route: the address part after the port, for example / or /profile.
  • View function: the Python function that runs for that route (home, profile).
  • Decorator: the line starting with @. It is the sticky label that connects a route to a view function.

1.3 The two rooms in our assignment

Our app.py has exactly two rooms. One is slow. The other is very slow. Everything in Q1 and Q2 depends on this difference, so let us draw it.

Part 2 • FoundationsTelling the time inside code

Two lines of Python do all the interesting work in Q1 and Q2. Let us take them apart.

2.1 time.sleep(10) – the freeze button

Story box • the statue game Your teacher shouts "STATUE!" and you must freeze completely for 10 seconds. You are not thinking, not moving, not talking. When she shouts "MOVE!" you carry on from exactly where you stopped.

time.sleep(10) is the word STATUE for a program. The program stops on that line, does nothing at all for 10 seconds, then continues to the next line.

Why would anyone deliberately waste 10 seconds? Because in a real app that line would be something genuinely slow: reading a huge file, training a model, generating a PDF report, calling another company's server. sleep is a stand-in that lets us practise with slow work without writing the slow work.

2.3 The golden order of the three lines

@app.route('/')
def home():
    time.sleep(10)                              # 1. FIRST freeze for 10 s
    return jsonify(datetime.now().second), 200   # 2. THEN read the clock
The single most important sentence in this assignment The clock is read after the sleep finishes. So the number you get is (time the function started) + (sleep duration), expressed as seconds only.

And the extra bits on that return line

Piece of codeWhat it means, in plain words
jsonify(...) Wrap the value in JSON, the common text format that browsers and servers both understand. jsonify(20) travels across the wire as the text 20.
200 The HTTP status code for "everything went fine". (404 = not found, 500 = server crashed.)
{'Access-Control-Allow-Origin': '*'} A permission slip called CORS. By default a browser refuses to let a page read data from a different address. The * means "anyone may read me". Without this line the fetch would be blocked and you would see a CORS error instead of a number. It does not change any timing.
debug=True Developer comfort: show full error pages and auto-restart when you edit the file. Also does not change the timing logic.

3.1 What is fetch?

Story box • two orders, one trip to the waiter You and your friend sit at the same table. You call the waiter once and say: "one dosa AND one biryani". The waiter writes both slips and walks off.

You do not wait for the dosa before ordering the biryani. Both orders are already in the kitchen within the same second. This is exactly what lines 2 and 3 do: two orders are placed back to back, in the same instant.
Definition box fetch(url) sends the HTTP request immediately, and instantly hands you back a Promise: a receipt token that says "your food is coming, hold on to this". JavaScript does not stop and wait. It runs the very next line straight away.

3.2 What is a Promise, really?

Story box • the food-court token At a food court you pay and receive a plastic token with a number. The token is not your food. It is a promise of food. You can walk around, order at a second counter, chat with friends. When your token buzzes, you collect the food.

res1 and res2 are two tokens. .then(...) means "when this token buzzes, do this". Writing .then does not make the food arrive faster; it only says what to do on arrival.

3.4 The rule that decides the ORDER of the console output

Golden rule The console prints in the order the replies arrive, not in the order the code is written. Whoever finishes first, prints first.

This one rule is what the whole of Q1 and Q2 tests. In both questions res1 finishes before res2, so res1's number is printed first. But which numbers appear depends on how many waiters the server has. That is Part 4.

Small print, so nobody can trick you The word "approximately" in the question is there because network travel and res.json() take a few milliseconds. A real run might show 21 instead of 20 if the machine is slow. In the exam you always ignore those milliseconds and use the clean arithmetic.

Part 4 • Questions 1 and 2One waiter, or many waiters?

Q1 and Q2 print the same app.py and the same index.html. Only one thing changes between them:

Question 1 has: 
app.run(debug=True)
Question 2 has: 
app.run(threaded=False, debug=True)

That one extra word, threaded=False, changes the answer. To see why, we need to understand what a thread is. Story first, as always.

4.1 What is a thread?

Story box • the waiter in the restaurant A thread is one worker who can carry out one job at a time, start to finish.

Restaurant A (many waiters). A new customer walks in, and the manager assigns a fresh waiter to that table. Ten customers, ten waiters. Your slow order does not block anybody else's order.

Restaurant B (exactly one waiter). There is one waiter for the whole restaurant, and he refuses to touch a second table until the first table is fully served. Everybody else stands in a line at the door, waiting their turn.

Both restaurants serve identical food. The only difference is how long you wait.
The fact you must memorise When you call app.run() in Flask, Flask quietly sets threaded=True for you. So plain app.run(debug=True) already handles requests at the same time. You get the one-waiter behaviour only if you switch it off yourself by writing threaded=False.

This has been the behaviour since Flask 1.0. In much older versions you had to write threaded=True yourself. Underneath, Flask hands your settings to the Werkzeug development server, whose own default was threaded=False – which is why the fact is worth memorising rather than guessing.
Trap box Many students believe the opposite: that Flask is single-threaded until you ask for threads. That belief gives the wrong answer to Q1. Remember the direction: Flask's default is already threaded. threaded=False is a downgrade you choose.
Question 1 1 mark

With app.run(debug=True), a user visits index.html at 10:10:10 AM. What will be logged in the console (approximately)?

  • A. 20, 50
  • B. 20, 40
  • C. 40, 40
  • D. 50, 50

Step-by-step solution

1Check the server mode.
The code is app.run(debug=True). There is no threaded word, so Flask uses its default, threaded=True. This is Restaurant A: many waiters. Requests are served at the same time.
2Set the starting clock.
The page opens at 10:10:10. test() runs instantly, so both fetch calls leave at 10:10:10. Call this moment t = 0.
3Follow request 1, the one to /.
Its own waiter starts at t = 0, sleeps 10 s, so it reaches the return line at t = 10, which is the wall-clock time 10:10:20.
datetime.now().second reads 20. It sends 20 back.
4Follow request 2, the one to /profile.
It has its own separate waiter, who also starts at t = 0 (it did not have to wait for request 1). It sleeps 30 s, reaching the return line at t = 30, which is 10:10:40.
datetime.now().second reads 40. It sends 40 back.
5Decide the printing order.
Request 1's reply lands at t = 10; request 2's reply lands at t = 30. Earlier arrival prints first, so the console shows 20 and then 40.
Answer to Question 1 Console output: 20, 40   =>   Option B
Because both requests are handled simultaneously: 10 s after 10:10:10 gives second 20, and 30 s after 10:10:10 gives second 40.

Why the other three options are wrong

OptionThe wrong belief behind it
A. 20, 50 This assumes /profile had to queue behind / (10 + 30 = 40 s of waiting, landing at 10:10:50). That is true only when threading is switched OFF. This is the answer to Q2, not Q1.
C. 40, 40 This assumes both routes finish at the same moment. They cannot: one sleeps 10 s and the other 30 s.
D. 50, 50 Mixes both mistakes at once: queueing and equal finish times.
Question 2 1 mark

Same files, but now the last line is app.run(threaded=False, debug=True). A user visits index.html at 10:10:10 AM. What will be logged in the console (approximately)?

  • A. 20, 50
  • B. 20, 40

Important – please read before the solution In your screenshot, option B (20, 40) is the one that was selected for this question, and there is no green "Answer is Correct" banner on it. Q1 and Q2 cannot both be B: the examiner changed the code on purpose so the answer would change. The correct answer here is A (20, 50). The next page proves it second by second.

Step-by-step solution

1Check the server mode – this is the whole question.
We now have threaded=False. This is Restaurant B: exactly one waiter. The server can hold only one request at a time; a second request must wait at the door until the first is completely finished.
2Decide who gets served first.
Both requests were fired at 10:10:10, but not in a random order. Line 2 of the script fires / and line 3 fires /profile, so / reaches the server a fraction of a second earlier. The single waiter therefore picks up / first, and /profile stands in the queue.
3Serve request 1 (/).
Starts at t = 0, sleeps 10 s, reaches the return line at t = 10, wall clock 10:10:20. Sends back 20. Identical to Q1 so far – the first request never notices the difference.
4Now serve request 2 (/profile) – here is the change.
The waiter is free only at t = 10. Only now does profile() begin. It then sleeps 30 s, so it reaches the return line at t = 10 + 30 = t = 40.
t = 40 after 10:10:10 is the wall clock time 10:10:50.
datetime.now().second reads 50. It sends back 50.
5Printing order.
Reply 1 lands at t = 10, reply 2 lands at t = 40. So the console prints 20 first, then 50.
Answer to Question 2 Console output: 20, 50   =>   Option A
With one thread the work is serialised: 10 s for /, then 30 s for /profile, so the second reply is read at 10 + 30 = 40 s after 10:10:10, i.e. 10:10:50.

A neat cross-check the examiner built in

Suppose you doubted step 2 and thought /profile might be served first. Then /profile would finish at t = 30 (second = 40) and / would finish at t = 40 (second = 50), so the console would print 40, 50. Look at the option list: 40, 50 is not offered. The only way to land on a listed option is the order we used: / first, then /profile. The options themselves confirm the reasoning.

Part 5 • Questions 3 and 4Redis: the lightning-fast notepad

5.1 First, why do we need Redis at all?

Story box • the almirah and the sticky note Imagine you are doing homework. Your big textbook is inside a locked steel almirah across the room. Every time you need a fact you must stand up, walk over, unlock it, flip pages, walk back. Very reliable, very slow.

So you copy the four facts you need again and again onto a sticky note next to your hand. Now looking them up is instant.
  • The steel almirah = a normal database on the disk (like SQLite, MySQL, Postgres).
  • The sticky note = Redis, living in RAM, right next to the processor.
A sticky note has a catch, though: if somebody opens the window, it blows away. RAM is the same – switch the power off and it is gone. Speed is bought with fragility.

5.2 RAM vs Disk: the size of the speed difference

People say "RAM is faster". You must feel how much faster, because that single fact is why Redis exists.

5.3 What does "key value pair" mean?

Story box • the school bag tag In a cloakroom every hook has a name tag, and one bag hangs on it. Say the tag out loud and you instantly get the right bag. You never search through all the bags.

The tag is the key. The bag is the value. Redis stores nothing but tag-and-bag pairs. This is why Redis is called a key-value store and not a table-based (relational) database. There are no rows, no columns, and no JOIN statements.

5.4 If RAM forgets everything, can Redis ever recover?

Yes – and this matters for one of the options. Redis can copy its memory onto the disk now and then, purely as a backup, so that after a restart it can refill RAM.

5.5 Two more Redis features you must know for Q4

Feature 1: expiry, also called TTL

Story box • the milk packet A milk packet has a "use before" stamp. Nobody has to throw it away by hand; the date decides. In Redis you may stamp any key with a countdown: "delete yourself automatically after 60 seconds". That countdown is called the TTL, short for Time To Live. It is perfect for one-time passwords, login sessions and cached pages.

Feature 2: authentication

Story box • the lock on the notepad A notepad lying open on a desk can be read by anyone walking past. Redis can be given a password (the requirepass setting), and newer versions can even create separate users with different rights (this is called ACL). So yes, Redis has authentication features – they are simply switched off in a fresh install, which is why you must remember to turn them on.

Part 6 • Question 5Celery: giving slow jobs to a helper

6.1 The problem Celery solves

Go back to Q2 for a second. One slow request made another user wait 10 seconds for nothing. Now imagine the slow job is not a fake sleep but something real: "generate a 200-page PDF report and email it". That could take 3 minutes. Should the user's browser sit there spinning for 3 minutes? Obviously not.

Story box • the tailor's receipt You give cloth to a tailor and ask for a shirt. The tailor does not make you stand at the counter for two days. He writes your job in his order book, hands you a receipt, and says "come on Friday". You leave immediately and get on with your life. Meanwhile his assistants pick jobs from the order book one by one and stitch them.
  • The order book = the broker (a queue of pending jobs).
  • The assistants = Celery workers, separate programs doing the slow work.
  • Your receipt = the task id, which you can use later to ask "is it done?".
  • The finished-shirt shelf = the result backend, where answers are kept.
Definition box Celery is a distributed task queue for Python. Your web app hands a slow job to a queue and replies to the user at once. Independent worker processes – possibly on completely different machines – pick jobs off the queue and run them. This style of work is called asynchronous or background processing.

6.2 The Celery picture you should be able to draw from memory

6.3 Which brokers can Celery use?

This is the point option C attacks. Redis and RabbitMQ are the two most common choices, and RabbitMQ is the default recommendation – but they are not the only ones. Celery also supports Amazon SQS, and has further transports such as Zookeeper and consul, plus a filesystem transport for local testing.

Part 7 • Questions 6 and 7Concurrency vs Parallelism

These two words sound like synonyms. They are not, and Q6 and Q7 exist purely to see whether you know the difference. Ten minutes here will earn you two marks forever.

7.1 The two stories

Story box • CONCURRENCY = one cook, three dishes Amma is cooking rice, dal and a sabzi with only two hands. She puts the rice on to boil, and while it boils she chops vegetables. Then she stirs the dal, then goes back to the vegetables. She is never doing two things in the same instant, but all three dishes are in progress at the same period of time, and all three land on the table together.

That is concurrency: dealing with many tasks over an overlapping stretch of time, by switching between them.
Story box • PARALLELISM = three cooks, three dishes Now Amma calls two neighbours. Three people stand at three stoves. At any single instant, three dishes are genuinely being cooked at once.

That is parallelism: actually doing many tasks in the very same instant. It needs extra hands – which for a computer means extra CPU cores.
Definition box – the exam wording
  • Concurrency: multiple tasks make progress over overlapping time periods, not necessarily at the same instant.
  • Parallelism: multiple tasks execute simultaneously, literally at the same instant, which requires multiple cores or processors.
  • Context switching: one core rapidly pausing task A, saving its place, and resuming task B. This is how a single core fakes doing many things at once.

Part 8 • Questions 8, 9 and 10Message queues and message brokers

8.1 What is a message queue?

Story box • the letter box You want to send your cousin a letter. You do not need to phone her first and check whether she is at home. You drop the letter in the post box and walk away. The letter waits safely in the box until the postman picks it up. Your cousin reads it whenever she gets home.

A message queue is that post box for programs.
  • The person posting = the producer or sender.
  • The letter = the message (a small packet of data).
  • The post box = the queue, which acts as a buffer holding messages temporarily.
  • Your cousin = the consumer or receiver.

8.2 Point-to-point vs publish-subscribe

Q8 mentions "point-to-point messaging". There are two delivery styles, and you must be able to tell them apart.

Question 8 1 mark • multiple correct

Which of the following statement(s) is/are correct regarding message queue?

  • A. Message queue provides communication between components in a distributed architecture.
  • B. It provides a buffer which temporarily store messages.
  • C. In general, a message in message queue is processed more than once in point-to-point messaging.
  • D. In general, a message in message queue is processed only once in point-to-point messaging.

Option-by-option reasoning

OptionVerdictWhy
ATRUE "Distributed architecture" just means the software is split into pieces that may sit on different machines. Letting those pieces talk to each other without being directly wired together is the main job of a message queue.
BTRUE A queue holds messages temporarily until a consumer takes them – that is the textbook definition of a buffer (Figure 8.1). Note the word temporarily: a queue is not long-term storage like a database.
CFALSE In point-to-point, once a consumer takes a message it is removed, so it is not processed again. "More than once" describes publish-subscribe, not point-to-point.
DTRUE Exactly the left panel of Figure 8.2: one message, one consumer, processed once. Note that C and D are direct opposites, so precisely one of them can be right.

8.3 What is a message broker, and why does it save connections?

Story box • the post office A message queue is one post box. A message broker is the whole post office: it owns many boxes, sorts letters, decides which van carries what, retries failed deliveries, and keeps records.

Now think about what life would be like without a post office. To write to 4 friends you would need your own private road to each of their houses. And if all 4 of you wanted to write to each other, the town would need a spider web of private roads. With a post office, everyone builds just one road – to the post office.
Do the arithmetic once and you will never forget it With 10 senders and 10 receivers: direct wiring needs 10 x 10 = 100 connections. Through a broker: 10 + 10 = 20. With 100 and 100 it is 10 000 versus 200. Fewer connections means less code, fewer failures, and far easier scaling.

Which of the following is/are true regarding message broker?

  • A. A message broker helps in reducing the number of connections between servers, if compared with many-to-many connections between servers.
  • B. It does not allow easier scalability, if compared with many-to-many connections between servers.
  • C. It can be used for batch processing of many similar types of requests.

Option-by-option reasoning

OptionVerdictWhy
ATRUE 16 connections become 8; 100 become 20. Exactly Figure 8.3.
BFALSE Read the little word not carefully. A broker does make scaling easier, because adding one more server costs one new connection instead of many. The statement claims the opposite, so it is false.
CTRUE Because messages pile up in a queue, a consumer can collect a whole batch and process them together – for example, sending 500 collected emails in one go. Batch processing is a standard broker use case.
DFALSE "All of the above" would require B to be true as well. Since B is false, D collapses automatically.

Trap box – the tiny word "not" Option B is the same fact as option A, just phrased negatively. Examiners love this. When you meet a negative option, rewrite it in your head as a positive sentence ("a broker does allow easier scalability"), decide whether that is true, and then flip your verdict once.

8.4 Synchronous vs asynchronous, the last idea you need

Story box • phone call vs text message A phone call is synchronous: both people must be free at the same moment, and you cannot do anything else while talking. If she does not pick up, your message does not get through at all.

A text message is asynchronous: you send it and immediately go back to your game. You do not need to know whether her phone is on, off, charging or out of signal. She replies whenever she can.

Message brokers are the text-message model. That is the whole of Q10.
Question 10 1 mark • multiple correct

Which of the following is/are true regarding message broker?

  • A. They serve as intermediary between applications, which allow senders to issue a message without knowing the state of the receiver.
  • B. They serve as intermediary between applications, which allow senders to issue a message only after knowing the state of the receiver.
  • C. Inter application communication is often asynchronous.
  • D. Inter application communication is often synchronous.

Option-by-option reasoning

OptionVerdictWhy
ATRUE This is the definition of a broker: an intermediary. You post the letter and walk away; the post office worries about the recipient. The sender needs no knowledge of the receiver's state.
BFALSE The exact opposite of A. If the sender had to check the receiver first, the broker would be pointless – you would be back to a phone call.
CTRUE Communication through a broker is asynchronous: send now, get handled later (Figure 8.4, right side). Note the honest word "often" rather than "always".
DFALSE The opposite of C. Synchronous messaging is the model brokers were invented to escape.

9.2 The one-page cheat sheet

Flask timing questions

  • app.run() and app.run(debug=True)  =  threaded. Requests overlap.
  • app.run(threaded=False)  =  one at a time. Requests queue up.
  • Formula: answer second = (start second + waiting time + own sleep) mod 60.
  • The clock is read after the sleep, so waiting time counts.
  • Console order = order of arrival of replies, not the order the code was typed.
  • jsonify, status 200, the CORS header and debug=True never change timing.

Redis

  • In-memory key-value store. All work happens in RAM; disk is only for backup.
  • Data types: string, list, hash, set, sorted set (and more).
  • Persistence: RDB snapshot or AOF log, so data can be reconstructed.
  • TTL: positive = seconds left, -1 = no expiry, -2 = key does not exist.
  • Has authentication (requirepass, and ACL users in Redis 6+).
  • Typical uses: caching, sessions, rate limiting, leaderboards, Celery broker.

Celery

  • Four pieces: producer (your app) • broker (queue) • worker • result backend.
  • Brokers: RabbitMQ, Redis, Amazon SQS and others – not just the first two.
  • Flower = monitoring dashboard. Celery Beat = periodic scheduler.
  • Clients and workers retry automatically when the connection drops.
  • Can use more than one broker in one system.

Concurrency and parallelism

  • Concurrency: overlapping time periods, not necessarily the same instant.
  • Parallelism: the same instant, needs multiple cores.
  • Parallel implies concurrent. Concurrent does not imply parallel.
  • Concurrency works on single-core (context switching) and multi-core (real parallelism).
  • They are not mutually exclusive.

Message queue and message broker

  • Queue = temporary buffer; it decouples producer from consumer.
  • Point-to-point: one message, one consumer, processed once.
  • Publish-subscribe: one message, every subscriber, processed many times.
  • Broker turns n x m connections into n + m, so scaling gets easier.
  • Broker communication is asynchronous; the sender does not check the receiver's state.
  • Brokers enable batch processing of many similar requests.

9.4 Practice questions

Cover the answers with your hand. If you can do these seven, you have genuinely learned Week 9 and not just memorised a key.

P1. Same app.py and index.html as Q1 (threaded), but the user opens the page at 10:10:45. What is logged?

P2. Same as Q2 (threaded=False), page opened at 10:10:45. What is logged?

P3. In the Q2 code, the two fetch lines are swapped so /profile is requested first. Page opened at 10:10:10. What is logged, and in what order?

P4. TTL mykey returns -1. Will the key be deleted in one second?

P5. A single-core machine runs three tasks that all finish within the same minute. Is that concurrency? Is it parallelism?

P6. You have 6 sender services and 5 receiver services. How many connections with direct wiring, and how many through a broker?

P7. A message is placed in a point-to-point queue with 3 consumers attached. How many consumers process it?

Answers to the practice questions

P1. 55, 15. Threaded, so both start at 10:10:45. / finishes at 10:10:55, second = 55. /profile finishes 30 s later at 10:11:15, and the seconds hand has wrapped past 59, so second = 15. (75 mod 60 = 15. This is the wrap-around case.)

P2. 55, 25. One thread: / finishes at 10:10:55 (second 55). /profile starts only then and runs 30 s, finishing at 10:11:25, so second = 25. (45 + 10 + 30 = 85; 85 mod 60 = 25.)

P3. 40, then 50. /profile is served first: 0 to 30 s, finishing at 10:10:40, so it logs 40. Then / runs from t = 30 to t = 40, finishing at 10:10:50, so it logs 50. The 40 is printed first because it arrived first, even though it belongs to the second fetch in the code.

P4. No. TTL -1 means the key exists with no expiry set, so it stays until something deletes it. TTL 1 would be the "gone in one second" case.

P5. Concurrency yes, parallelism no. On one core the tasks take turns through context switching, so their time periods overlap but no two ever run in the same instant.

P6. Direct wiring: 6 x 5 = 30 connections. Through a broker: 6 + 5 = 11.

P7. Exactly one. In point-to-point the first consumer to take the message removes it from the queue; the other two never see it. (In publish-subscribe, all three would receive it.)

9.5 Glossary of every term used in this paper

TermMeaning in one sentence
ClientThe program that asks; usually your browser.
ServerThe program that answers; here, Flask on port 5000.
RouteThe path part of a URL, such as / or /profile.
localhost / 127.0.0.1A nickname meaning "this very computer".
PortA numbered door on a computer; Flask's development server uses 5000.
CORS headerA permission slip letting a page read data from another address.
PromiseA token in JavaScript standing for a result that will arrive later.
ThreadOne worker inside a program, able to run one job at a time.

ConcurrencySeveral tasks progressing over overlapping periods of time.
ParallelismSeveral tasks running in the very same instant, on several cores.
BlockingBeing forced to wait, unable to do anything else meanwhile.
SynchronousSend and wait for the reply before continuing (a phone call).

9.6 Final word

If you remember only five sentences from this whole book
  1. Flask's app.run() is threaded by default; threaded=False makes it queue.
  2. The clock is read after the sleep, so waiting time is part of the answer.
  3. Redis works in RAM, stores key-value pairs, and TTL -1 means "never expires".
  4. Parallel implies concurrent, never the other way round.
  5. A broker turns n x m connections into n + m, and lets senders fire and forget.
